# NanoLED v1 / v2：コントローラ通信仕様（実装者向け）

Webアプリの「コントローラ」タブと、M5NanoC6／AtomS3Lite上で実行するBLEプログラムの共通仕様。USBでの書込みとは別の通信で、接続だけではプログラムを書き換えない。対象機種・UIFlow2版ごとに実機確認が必要であり、NanoC6での確認をAtomS3Liteの確認として流用しない。イベント参加・キットIDは不要だが、自宅利用でもAIへ渡す確認済みBLE基盤の要件は同じ。

画面は日本語・英語・簡体字中国語に切り替えられるが、通信仕様は言語によって変えない。`NanoLED-` という名前の接頭辞、UUID、ASCIIコマンド、JSONキー、モード名・HEXデータは両機種で共通のまま維持する。名前にNanoと含まれていてもNanoC6専用とは限らない。

**この仕様は、従来の任意のBLE基準コードと自動的に互換になるものではない。** 本リポジトリには、対象のUIFlow2ファームウェアで実機確認済みのBLE基準コードは含まれていない。一方で、実機未確認のNanoLED v2候補を同梱している。「AIの準備」でWebコントローラを有効にすると、通常利用者は基準コードの登録なしで候補を準備し、明示的に実行して試せる。AIの準備文にも候補全文と未確認の注意を含める。独自の確認済み基準コードを作る実装者は [prompt.md のプロンプトE0](../prompt.md) を使い、手元の確認済み基準コードへ本仕様を組み込み、実機確認してから確認済みとして登録・配布する。未確認のAPIやライブラリを推測して置き換えない。

## v2：作品専用リモコン

「作品づくり」の候補実装は `firmware/starter/runtime.py` と `StarterProgram.ts` にあり、「AIの準備」の `ControllerStarter.ts` も同じ生成器を利用する。提供側の確認記録は現在空で、実機検証済みコードの同梱を意味しない。設定が有効なら未確認でもコードの準備・表示・保存ができ、この段階ではUSBへ送信しない。機器で試すには別途USB接続と実行操作が必要で、未確認候補は毎回、機器・UIFlow2版・LED設定・配線・電源と、実行による動作中プログラムの停止・`main.py`の保存し直しを確認する。キャンセル時はその実行操作による機器の停止・書込み・起動を行わない。[実機受入手順](starter-validation.md)を参照。作品ファイルの利用者確認やブラウザのボタン名保存から、提供側の検証記録を作成することはできない。候補をAIの相談に使えることと、実機確認済み基準コードとして登録できることは別である。

有効な登録済み基準コードがある場合は候補より優先し、v1の確認をv2に自動で変えない。未登録・失効・非対応で候補へ切り替える場合も、元の基準コードと確認情報は変更しない。未準備・範囲外の設定では、機器・LED設定を確認してから準備する手順を案内する。詳細な操作は [AIの準備ガイド](ai-preparation.md#webリモコンをまず試す) を参照。

Web画面で保存するボタン名・アイコンは表示専用。v2の受信カタログに存在するIDだけに適用し、`MODE` / `ACTION` とIDはそのまま送る。機器からの報告名、作品ローカルの表示名、通信IDは同一とは限らない。v1の独自コマンド欄の仕様やRGB指定コマンドは変更しない。

v2は状態確認・明るさ・再生／停止・モード切替・一度だけのアクションを扱う。受信した `v` で画面を選ぶ。v1は後述の旧仕様のまま利用できるが、v2専用操作は無効状態の案内として表示し、送信しない。既存の `nanoLedV1` 実機確認はv2へ自動移行せず、別途確認して `nanoLedV2: true` を登録する。コード・機種・UIFlow2版・LED条件を変更したときは再確認が必要。

### 接続とコマンド

1節の名前・UUID・RX応答ありWrite・TX Notify・購読後のSTATUS・再接続手順は共通。コマンドはASCIIのLF終端で **LF込み20バイト以下**、直列に書く。受信側はLFまで蓄積し128バイト超の行は次のLFまで捨てる。受信キュー・待機・再試行は有界。無効な引数や未定義IDでは状態を変えず、ログはUSBへ出す。

| コマンド | 機器での意味 |
| --- | --- |
| `PLAY` | 保存した基底モードの位相から再開。消灯中は選択中モードを再生 |
| `PAUSE` | アニメーション・点灯フェードの進行を止め、現在の表示色と位相を保持。消灯フェードは止めない |
| `OFF` | 現在の出力から200msで全LEDを黒へ。アクションと点灯フェードを中止、選択モード・明るさ設定は保持 |
| `MODE <id>` | 定義済みモードを選び、演出をリセットして再生 |
| `ACTION <id>` | 定義済み演出を非ブロッキングで1回実行。演出中でも同IDは再スタート、別IDは切替。最後に最初の演出前のモード・再生状態へ戻る |
| `BRIGHTNESS n` | 0〜100整数。100は設定した安全上限の100% |
| `SPEED n` | 0〜100整数。速度対応時だけ適用。0は最遅で停止ではない |
| `STATUS` | 動作を変えず現在の状態を通知 |

アクション前が停止中なら元の凍結位相、消灯中なら消灯へ戻す。実行中も有効な追加 `ACTION` を受け付け、同じIDなら再スタート、別のIDなら新しい演出へ切り替える。連打をあとから再生する演出待ちキューは作らず、最新の有効な要求に切り替える。`MODE` / `PLAY` / `PAUSE` / `OFF` はアクションを中断する。`PLAY` は基底モードを再開、`PAUSE` は中断時に実際に見えていた補間途中のフレームを保持する。必要なら保持フレームと再開用の基底モード位相を別に保存する。停止は消灯でもUSBのプログラム停止でもない。

消灯中の明るさ・速度変更では点灯しない。停止中の明るさ変更は位相を進めず保持フレームへ倍率を適用する。全出力で安全上限を守る。速度対応時の標準周期は `period_ms = 3000 - 29 * n`。起動既定値は `playback=off`、`action=null`、`brightness=100`、`speed=0`、`mode` は最初の定義済みモード。

### アクションの再スタート・切替

- **追加ACTIONを一律に無視しない。** 有効な受信行を主ループで処理した時点で、同IDなら演出時間をリセット、別IDなら新しい演出へ切り替える。不正なID・引数は現在の演出、経過時間、復帰元を変えない。
- 再スタート時は **最後に実際に送信した全LEDのRGB出力** を開始点にする。途中で黒や基底モードの初期フレームへ戻さず、新しい演出の出力へ有限時間の非ブロッキング補間でつなぐ。同梱SPARKLE候補では `ACTION_RESTART_BLEND_MS = 200`。独自の演出でも、現在の色・明るさから自然につなぐ時間・方法を作品仕様で定める。
- 原点の実出力には既に安全上限・明るさ・フェードが適用されている。これらを二重に掛けない。新しい演出の出力と補間結果も安全上限を守り、途中の明るさ変更を処理できるようにする。再スタート直後にそれ以外の設定変更がなければ同じ出力を保つ。`pixels` は補間目標ではなく実際の最終送信値を報告する。
- 復帰元は **最初のACTIONより前** の基底モード・位相・再生状態・保持フレーム。再押下で実行中アクションの途中状態を復帰元へ上書きせず、最新の演出が完了したときに一度だけ戻す。同梱SPARKLEは最後の受付から約1秒で完了する。最初がpausedなら元の凍結フレーム、offなら消灯へ戻る。
- 演出の重ね掛け、再帰呼出し、無制限の予約・再試行はしない。RXの有界通信バッファと、演出終了待ちの予約キューは区別する。受信行は従来どおり順に処理するが、追加ACTIONは進行中の演出を即時置換し、古い演出の完了を待たない。
- 補間中もBLE・本体ボタン・通知を処理する。`MODE` / `PLAY` / `PAUSE` / `OFF` と安全停止で補間状態を破棄し、遅れて古い演出が復活しない。OFFはその時点の実出力から既存の200ms消灯フェード、PAUSEは実出力を保持して通常の明るさ調整を可能にする。初回off→ACTIONの最低200msフェードインと即時安全消灯も維持する。
- Web画面は受信した `action` が非nullでもアクションボタンを有効にする。ただし未接続・状態未受信・更新停止・送信処理中のガードは維持する。自動再送やブラウザからの連続輝度コマンドで補間を作らない。

**この項目は追加ACTIONを無視していた旧v2の動作を改訂したもの。** UUID・コマンド・JSON形式・`v=2`は変えていないため、旧プログラムでは再押下しても無視される場合がある。Web更新・BLE再接続だけでは機器上のコードは変わらず、対応コードを明示的に準備・USB書込み・実行し、対象機器で確認する必要がある。既存作品・登録済み基準コード・実機確認記録を自動更新しない。v2のバージョン表示だけで再スタート対応済みと判定しない。

### Webリモコンの200ms消灯フェード（v1/v2共通）

- ブラウザは従来どおり `OFF\n` を1回送る。`BRIGHTNESS` を連送して段階的に下げたり、明るさ設定を0へ書き換えたりしない。
- 機器側に `REMOTE_OFF_FADE_MS = 200` を置く。OFF受付時の **最後に実際に送信した全LEDのRGB出力** を固定し、その値へ `max(0, 1 - elapsed / 200)` を掛けて黒へ進める。目標色から作り直さず、安全上限・明るさを二重に掛けない。停止中やアクション中でも、その時見えていた出力から始める。
- `time.ticks_ms()` / `time.ticks_diff()` と主ループで非ブロッキングに進める。長いsleepやBLE受信コールバック内での演出は使わず、BLE・本体ボタン・通知処理を継続する。アクションとフェードインは取り消し、選択モード・明るさ設定は保持する。
- 再度のOFFで再開始・延長しない。PAUSEでも消灯完了まで進める。BRIGHTNESS/SPEEDは設定だけを更新し、消えかけの出力を明るくしない。新しい点灯要求（v2のPLAY/MODE/ACTION、v1の点灯モード）は消灯フェードを中断して処理する。
- `pixels` は途中も最後に送信した出力を報告する。v2は完了まで `playback=playing`、`action=null` とし、黒を送信してから `playback=off` を通知する。v1は完了まで直前の `mode` を保持し、黒を送信してから `mode=OFF` とする。すでに全出力が0なら直ちに消灯状態へ移ってよい。消灯完了後も最新状態を通知し、Write応答だけを消灯完了としない。
- 起動時・例外・KeyboardInterrupt・安全停止の消灯は即時のまま。本体ボタンの設定済み消灯動作は変更しない。消灯→点灯時の最低200msフェードインは別の規則として維持する。

**既存プログラムは自動更新されない。** コマンドやJSONの形式は変えないため、旧プログラムにもOFFは届くが、旧実装では即時消灯することがある。200msフェードアウトを使うには対応コードを準備し直し、利用者がUSBで明示的に書き込み・実行し、対象機器で確認する。Webページの更新・BLE再接続だけでは反映されない。既存作品・登録済み基準コード・実機確認記録を黙って置き換えない。

### 必須の状態通知

```json
{"v":2,"mode":"RAINBOW","brightness":50,"speed":30,"pixels":"100000","playback":"playing","action":null,"controls":{"speed":true,"modes":[{"id":"RAINBOW","label":"にじいろ"}],"actions":[{"id":"SPARKLE","label":"キラッと光る"}]}}
```

例はLED1個。実機では全LED分を報告する。

- `v`: 数値2。`brightness` / `speed`: 適用した0〜100整数。`pixels`: 3節と同じRGB・1〜300個の最終送信値で、発光の測定ではない。
- `mode`: 常に `controls.modes` 内のID。消灯中も選択を保持し、`OFF` をモードIDにしない。
- `playback`: `playing` / `paused` / `off`。`action`: `null` または `controls.actions` 内の実行中ID。非nullなら `playback=playing`。`off` なら `action=null`、`pixels` は全桁0。
- `controls`: 毎回全体を通知。`speed` はbooleanで、falseならブラウザは速度欄を隠し機器はSPEEDを無視する。
- `modes`: 1〜8件、`actions`: 0〜8件。各要素は `{id,label}`。IDは `^[A-Z][A-Z0-9_]{0,11}$`、同じリスト内で重複不可。予約語: `OFF` / `PLAY` / `PAUSE` / `STATUS` / `BRIGHTNESS` / `SPEED` / `MODE` / `ACTION`。
- `label`: 制御文字のない1〜24 Unicodeコードポイントの平文。プログラムで決めた利用者向け名称であり、HTMLとして解釈せず、UI言語変更で翻訳しない。

TXは **UTF-8 JSONのLF終端、エンコード後4096バイト以下（LF除外）**。v1のASCII制限をUnicodeラベル用に拡張する。文字数でなくバイト数で制限する。Notifyは1回20バイト以下で、Unicode文字の途中で分割されてもよい。ブラウザはLFまでバイト結合してから厳密に復号する。不正UTF-8・不正JSON・過大行で既存状態を上書きしない。

3節の分割・最大5件/秒・約1秒ごとの定期通知・送信中行の維持・待機は最新1件・切断時破棄を維持し、アクション開始・再スタート・切替・終了でも通知する。初回未受信・更新停止中は状態未確認として案内する。初回有効状態までOFF以外は操作不可。

**Write Responseは実行ACKではない。** v2には要求ID・完了履歴がないため「送信」と「実行確認」は区別する。アクション表示は受信した現在の `action` のみ。同IDの再スタートは `action` の値が変わらないため、同じIDの通知だけで個別の再実行受付・完了を確認したとは扱わない。短いアクションが通知で観測されなくても成功／完了と断定しない。実行受入は状態通知と実際のLEDの両方で行う。

4節のbitstream・GRB・安全上限・GPIOを維持する。v2では「OFF状態」を `playback=off` と解釈する。起動・PLAY・MODE・ACTIONで消灯かつ全出力0から点灯するときは最低200msの非ブロッキングフェード。点灯中の変化・一時的黒フレームで再開始せず、フェード中のモード変更では進行度を維持する。

### v2実機受入（未実施はNOT RUN）

5節の機種・接続・ピクセル対応・負荷・再接続確認に加え、以下を確認する。5節の固定モードはv1検証時だけ使う。

- 日本語・英語・中国語ラベルが20バイト境界をまたいでも欠損せず、カタログ制約と4096バイト上限を満たす。
- 再生→停止で色と位相を保持し、再生で続く。リモコン消灯は直前の出力から200msで黒になり、途中はoffを報告しない。明るさ設定と選択モードは保持する。消灯→PLAY/MODE/ACTIONに200ms以上のフェードインを適用。
- 停止中・アクション中・フェードイン中のOFF、OFF連打、消灯中のPAUSE・スライダー、新しい点灯要求による中断を確認する。消灯中もBLEとボタンが応答する。
- 各モードはリセットして再生。各アクションは1回実行後、元の再生中・停止中・消灯中へ戻る。演出中の同ID再押下・別ID切替では、その時見えていた出力から自然につなぐ。再押下を繰り返しても最初の復帰元を維持し、最後の演出だけが完了して戻り、古い演出を後から実行しない。未定義IDでは演出時間も変えない。
- 補間開始直後・中間・終了時、点灯フェード中、一時的黒フレーム、明るさ0/50/100・補間中の変更、時刻カウンタ周回付近でも出力が急に初期化されず、安全上限を守る。同梱SPARKLE候補は200ms補間・最後の受付から約1秒で完了する。
- アクション中のMODE/PLAY/PAUSE/OFFによる中断、停止フレーム保持、PLAYの基底モード復帰。
- 明るさ0/50/100、停止中の明るさ変更、速度対応あり／なし、消灯中の変更でも安全上限・停止位相・消灯を保つ。
- 初回未受信と更新停止の案内、Write成功と実行成功の区別、状態報告と物理発光の個別確認。
- v1の従来操作・確認記録を維持し、v2命令を送らずv2確認済みと扱わない。

以下の2・3節は **旧v1のコマンドとJSON**。v2は上記の定義を使い、1・4節の共通条件を維持する。

## 1. 接続

機器はPeripheral、ブラウザはCentral。名前は **`NanoLED-` で始まる、確認済み基準コードの実際の名前** を維持する。キットIDから名前を作る必要はなく、アプリは基準コードの名前を自動で変更しない。新しい名前の設定を明示的に依頼するときの例は `NanoLED-M5NanoC6` / `NanoLED-AtomS3Lite`。この例は一意なIDではなく、同名の機器が複数あり得るため、自分の機器の電源で出現・消失を確認して見分ける。

ブラウザが完全名で見つけられるよう、対象ファームウェアの確認済みAPIを使って広告またはscan responseに名前を含める。ブラウザは名前の接頭辞 `NanoLED-` で検索し、サービスへのアクセス権を別途要求する。以下のサービスとCharacteristicは接続後に必須だが、サービスUUIDの広告は任意。完全名と128-bit UUIDを同じ広告パケットへ無理に詰め込まず、未確認の広告APIを推測しない。

| 用途 | UUID | 必須のプロパティ |
| --- | --- | --- |
| サービス | `6e400001-b5a3-f393-e0a9-e50e24dcca9e` | Primary service |
| RX：ブラウザ → 機器 | `6e400002-b5a3-f393-e0a9-e50e24dcca9e` | Write（応答あり） |
| TX：機器 → ブラウザ | `6e400003-b5a3-f393-e0a9-e50e24dcca9e` | Notify |

UUIDが同じだけではNanoLED v1対応とは判定できず、以下のコマンドと状態通知の形式も一致させる必要がある。RXのWrite Without Responseだけ、TXのReadだけでは対応しない。TXのRead対応は任意。

ブラウザは利用者の接続ボタンから機器を選択し、TXの通知を有効にしてから `STATUS\n` を送る。初回の正しい状態を受信するまで、点灯モードのボタンとスライダーは有効にしない。ただし安全のため、「消灯」（`OFF`）は接続できていれば状態未受信でも送れる。消灯コマンドの送信成功だけで、実際の消灯や状態受信の成功とは判断しない。切断時にはGATTオブジェクトと受信途中のデータを破棄し、次の接続でサービスとCharacteristicを取り直す。

対応環境の目安はWindows/macOSのChromeまたは対応するデスクトップEdge、AndroidのChrome。iPhone/iPadの標準ブラウザ、Safari、Firefoxの標準機能は対象外。HTTPSまたは `localhost`、OSのBluetooth有効化、ブラウザへの許可が必要。対応状況は [Chromeの公式ガイド](https://developer.chrome.com/docs/capabilities/bluetooth) と [Web Bluetoothの実装状況](https://github.com/WebBluetoothCG/web-bluetooth/blob/main/implementation-status.md) を参照する。USB書込みはPC版Chrome/Edgeを使用する。

## 2. コマンド

UTF-8のASCII文字列。**1コマンドをLF（`\n`）で終端する。** 1行はLF込み20バイト以下。ブラウザは1行ずつ応答ありWriteで順番に送り、同時書込みしない。応答ありWriteの成功は通信上の受付であり、LEDへの反映成功ではない。

| 送る文字（末尾にLF） | 意味 |
| --- | --- |
| `PINK` | 全体をピンクにする |
| `BLUE` | 全体を青にする |
| `MAGIC` | ピンク・紫・青の光を左から右へ流す |
| `RAINBOW` | 全体をレインボー変化させる |
| `OFF` | 現在の出力から200msで全LEDを消灯。明るさ設定を保持し、プログラムとBLEは継続する |
| `BRIGHTNESS n` | 明るさの割合を設定。`n` は0〜100の整数 |
| `SPEED n` | アニメーションの速さを設定。`n` は0〜100の整数 |
| `STATUS` | 現在の状態をTXから通知。動作は変更しない |

標準モードはすべて実装する。独自の追加モード名は `^[A-Z][A-Z0-9_]{0,15}$` に一致する半角英大文字・数字・アンダースコア、最大16文字。`STATUS`、`BRIGHTNESS`、`SPEED`、`PLAY`、`PAUSE`、`MODE`、`ACTION` は予約語であり、モード名に使わない。標準4モードと従来スライダーは互換だが、旧独自名PLAY/PAUSE/MODE/ACTIONは新画面から送れない。該当時は基準コードを自動変更せず実装者へ改名を確認する。追加演出は機器側への実装が必要。

`BRIGHTNESS 100` は、準備画面で設定した `MAX_BRIGHTNESS_PERCENT` の100%を意味する。例：安全上限50%・スライダー50なら物理出力の上限は25%。**安全上限そのものを変更しない。** 値0で暗くしても現在モードを維持する。OFF中の明るさ・速さ変更は設定だけを更新し、勝手に点灯しない。

`SPEED 0` は停止ではなく最もゆっくり、`SPEED 100` は最も速い。標準MAGIC/RAINBOWは `period_ms = 3000 - 29 * n`（0で3秒、100で0.1秒）の周期で位相を進める。LED数で1周期が変わらないようにする。追加演出でも0は停止にせず、0〜100の同じ向きで速さを反映する。指定が省略された場合の標準の起動状態は `mode=OFF`、`brightness=100`、`speed=0`。起動時の光り方などを利用者が明示した場合は、その指定を安全上限とOFF→ONフェードの範囲内で適用できる。通知は標準値を固定で返さず、実際の適用状態を返す。

受信コールバックでは受信バイトを有界キューへ保存するだけにする。メインループで分割データを結合し、LFまで届いた行だけを処理する。1回の受信に複数行がある場合も順番に処理し、1つの変数への上書きでコマンドを落とさない。受信行のバッファ上限は128バイトとし、上限超過時はその行を次のLFまで破棄する。コマンドキューも有界とし、満杯なら追加分を破棄して診断を出す。長い待機や無制限の再試行をしない。

完全な行をUTF-8として検証し、前後の空白・CRを除去、大文字化して判定する。未知のコマンド、引数不足、小数、範囲外、復号エラーでは状態を変更せず、可能なら短い診断を出す。ボタンとBLEは共通のモード変更処理を使用する。

## 3. LED状態の通知

TXへ **ASCIIだけのJSONを1行、末尾にLF** で送る。ログやデバッグ文字列はTXへ混ぜず、USB側へ出す。

```json
{"v":1,"mode":"PINK","brightness":50,"speed":0,"pixels":"3f001f3f001f"}
```

この例はLED2個分の形式例で、実際には固定設定のLED数分を送る。全フィールド必須。

| フィールド | 型・意味 |
| --- | --- |
| `v` | 数値の `1`。通信仕様の版 |
| `mode` | 現在適用中のモード名。上記のモード名形式に従う |
| `brightness` | 機器が適用した明るさ設定、0〜100の整数 |
| `speed` | 機器が適用した速さ設定、0〜100の整数 |
| `pixels` | LED1から順に、各LEDを `RRGGBB` の6桁HEXで連結した文字列 |

`pixels` は **安全上限・スライダー・フェードをすべて反映し、最後にLEDへ送信したRGB値**。目標色や処理前の値を報告しない。WS2812への送信バッファは従来どおりGRB順だが、通知ではRGB順へ戻す。全消灯なら全桁を `0` にする。HEXは大文字・小文字どちらも可。

対応LED数は1〜300個、1個3チャンネルのRGB LED。LED数は `pixels.length / 6` で判定する。使用するLEDが300個超またはRGB以外の場合、GPIO・LED数・BPPを勝手に変更せず対応範囲を確認する。SK6812 / SK6812MINIの選択はRGBW対応を意味せず、RGBWへ自動変換しない。1行の最大長はLFを除いて4096バイト。短縮・間引きでLED数を偽らない。

この表示は機器が報告する送信済み出力のスナップショットであり、LEDの実発光をセンサーで測った結果ではない。配線・故障・色順は実機で確認する。ブラウザはモード・明るさ・速さ・LED表示を受信状態から更新し、送った設定だけで現在のLED表示を塗り替えない。

### 分割と頻度

- 既定MTU23でも動くよう、1回のNotifyデータは20バイト以下に分割する。1行末尾のLFは最後のチャンクに含める。
- 複数スナップショットのチャンクを混ぜない。送信開始時に固定した1行を最後まで送り終えてから次を送る。
- LEDアニメーション・ボタン・コマンド処理を止めず、メインループから少量ずつ送る。通知の送信待ちや失敗時の再試行も有界にする。
- `STATUS`、コマンド適用、本体ボタンによる変更を契機に最新の状態を通知する。変化がなくても約1秒ごとを目安に通知し、最大5スナップショット/秒に抑える。
- LED数や通信速度のため送信に時間がかかる場合は周期を延ばす。送信中の行は維持し、待機分は最新1件だけにまとめる。古い状態を無制限にためない。行の途中で別のJSONへ切り替えない。
- 切断で送信途中の行を破棄する。再接続・通知再購読後は完全な新しい行から送る。

ブラウザはNotifyの境界ではなくLFで行を区切る。分割、複数行の同時受信、不正JSON、過大行を扱い、正しくない行で現在の状態を上書きしない。状態が届かない間は「未受信」または「更新が止まっている」と示し、古い表示を現在の測定値として扱わない。

## 4. ハードウェア上の固定条件

[prompt.md](../prompt.md) と選択機器の `boardId` に従い、外付けLEDは利用者設定の `ledPin`（初期値はGrove G2 / GPIO2）、本体ボタンは **M5NanoC6ならGPIO9、AtomS3LiteならGPIO41**（両方active LOW）とする。利用者が設定したLED型番・LED数・最大輝度、`machine.bitstream()`、800kHz用の固定タイミング、GRB送信は維持する。`neopixel`を追加しない。

外付けLEDを内蔵LEDへ置き換えない。M5NanoC6の内蔵RGBはGPIO20、RGB電源制御はGPIO19、青色LEDはGPIO7。AtomS3Liteの内蔵RGBはGPIO35で、NanoC6の電源制御ピンを流用しない。配線は [M5NanoC6](https://docs.m5stack.com/en/core/M5NanoC6)／[AtomS3 Lite](https://docs.m5stack.com/en/core/AtomS3%20Lite) の公式資料と照合する。

OFF状態かつ全LED出力0から点灯モードへ移るときは、起動直後を含めて最低200msの非ブロッキングフェードを適用する。点灯中の色変更、明るさ変更、アニメーション中の一時的な黒フレームでは再開始しない。OFFコマンドはフェードインを取り消し、上記「Webリモコンの200ms消灯フェード」に従って消灯する。起動時や例外・安全停止の即時消灯とは区別する。

## 5. 受入確認（実機）

以下は自動テストではなく、対象ファームウェア・実際のLED・対応ブラウザで行う。未実施なら `NOT RUN` と記録する。

- 対象機種・UIFlow2版・LED構成を記録し、ボタンと外付けLEDのピンが上記の機種別定義に一致する。

- 自分の機器を見分けて選び、接続・初回状態受信・切断・再接続できる。同名の機器がある場合も取り違えない。
- PINK/BLUE/MAGIC/RAINBOW/OFFがすべて反映され、OFF後も接続とボタンが使える。
- リモコンOFFは最後の出力から200msで黒へ進み、明るさ設定を0へ変更せず、完了後にmode=OFFを報告する。OFF連打で延長せず、フェード中も操作・通知が処理される。
- 明るさ0/50/100でも安全上限を超えず、OFF中にスライダーを動かしても点灯しない。
- SPEED0でも演出が進み、100より遅い。OFF→ONの200ms以上のフェード中も操作を受け付ける。
- 本体ボタンだけで変更した状態もブラウザに届く。全LEDの位置と色が報告値と対応する。
- 20バイト分割、速い操作、長いLED列でもJSONが混ざらず、LED更新を長時間止めない。
- USBの実行・停止・更新・リセットでBLEが切れた場合に再接続できる。タブ切替だけではプログラムを停止しない。
- 古いUUID、TXなし、異なるJSONでは「接続したから正常」と扱わず、未対応・未受信として案内できる。
