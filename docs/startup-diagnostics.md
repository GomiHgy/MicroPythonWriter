# 起動クラッシュの診断とUSB操作の復旧

## 何を調べる機能か

USBの転送・構文確認が成功しても、作品の起動後にファームウェア内部でクラッシュして再起動する場合がある。例えば `Guru Meditation Error` は通常のPython例外とは別で、Pythonの終了応答が届かないことがある。

Webアプリは常駐プログラムと、BLE先行準備を含む有限Raw REPLコマンドの出力中の `A fatal error occurred. The crash dump printed below`、`Guru Meditation Error: Core ... panic'ed (...)`、`ESP-ROM:esp32...`、`MPY: soft reboot` を、分割されたUSBデータから検出する。異常終了として実行中表示を解除し、古い常駐セッションを破棄する。停止操作中でも正常停止にしない。機器への保存が確認済みなら書き込み成功は保持する。先行準備中の異常終了なら、まだ新しいファイルは書き込んでいない。

クラッシュ後の新しい書き込み・実行・リセットはRaw REPLの明示的な再取得まで拒否する。自動再実行・自動リセット・自動起動設定変更は行わない。検出はシリアル文字列によるもので、機器内部の監視や原因の特定ではない。同じファームウェア出力を作品が意図的に行った場合は区別できない。また、通信が先に失われてログが届かない場合はUSB切断の案内になる。

## 利用者の手順

「プログラム」画面の下部にある **起動時に再起動する場合の診断（必要なときだけ）** を開く。通常は閉じている。
本体の異常終了を検出した場合は、操作結果の **エラーの詳細・対処を見る** から診断欄を開ける。

1. **元コードを保存** を押し、`main-original.py` がダウンロードできたことを確認する。元コードを別ファイルに保管した確認にチェックする。ダウンロード開始だけでは保存完了の証明にならない。
2. **診断版をコード欄へ入れる** を押す。元コードの保管確認が必要で、コード欄だけを番号付きログのある診断版に置き換える。この操作ではUSB接続・機器への書き込み・停止・実行を行わない。別ファイルも必要なら **診断版を保存** で `main-diagnostic.py` を保存できる。ファイル保存だけではコード欄の内容は変わらない。
3. 元作品のバックアップがある状態で、機器の電源を完全に切って入れ直し、USB接続して **実行** を1回だけ押す。本体ボタンやBLEを操作しない。通常の元コードではなく、準備した診断版がコード欄にあることを確認する。
4. 最初の `[MPW DIAG 00] FILE_ENTER`、`[MPW MEM ...]`、各初期化の `BEFORE / AFTER` を確認する。起動・異常終了のログが出たら **診断ログを保存** で `MicroPython-diagnostic-log.txt` を保存する。アクセスコード・Wi-Fi情報・資格情報などを確認し、共有前に必要に応じて伏せる。ログは自動送信しない。
5. 診断後は **保管した元コードへ戻す** で元コードをコード欄へ戻す。ブラウザの再読込などで保管内容が失われた場合は、保存した `main-original.py` の全文をコード欄へ戻す。これはコード欄だけの操作で、機器へ戻すには別途利用者が明示的に実行する。

**実行は機器のmain.pyを上書きする。** 自動実行がONなら次の電源投入時にも診断版が動く。診断ファイル作成では起動設定を変更しない。機器内の `.bak` は次の書き込みで変わるため、それだけを原本保管先にしない。

## 診断版が追加すること・しないこと

- 元の文・コメントを置換せず、構文木で特定できる文の前後に `[MPW DIAG NN] ... BEFORE / AFTER` を挿入する。複数行の引数とインデントを維持する。module docstringとfuture importも維持する。
- ハードウェアimport、Pin、bitstream、BLE構築・有効化・MTU/GATT/広告の設定、対応する作品の初期化・最初の更新を対象にする。同じログ地点は最初の1回だけ記録する。最大32文を対象にし、ループごとの無制限出力を避ける。
- Pythonの使用量・空き量とESP-IDFのヒープ領域の `(総量, 空き, 最大空きブロック, 過去の最小空き)` を別々に記録する。APIがなければ `unavailable`。両者を合算しない。
- 構文エラー・診断用変数名との競合では生成しない。一行suiteやセミコロンで並べた文などは変更せず、対象数・省略数を表示する。任意のalias・動的API呼び出しをすべて追跡するものではない。
- GPIO・LED数・最大輝度・演出・引数・無線の設定を変更しない。Wi-Fi停止・BLE先行有効化・GC強制回収・リセット・追加sleepを対策として加えない。

ログ関数・観測モジュールの読み込み・計測自体がメモリ使用量やタイミングを変える。BEFOREとAFTERが揃わない地点は調査の手掛かりであり、そのAPIが原因であるとの証明ではない。診断版が動いても元作品の問題解消や提供側の実機確認済みにはしない。正確なネイティブ関数の特定には対象ファームウェアと一致するELFが必要。
番号はソース内の位置を示すため、分岐・例外処理・後始末では番号順に出ない場合がある。

## Androidで共有されたログの判断例（2026-10-08）

利用者が共有した47,760バイトの作品と実行ログでは、転送サイズ・保存後のサイズが一致し、`__M5_COMPILE_OK__` の後に `Guru Meditation Error: ... (Load access fault)` と機器の再起動が記録された。ここから確認できるのは、転送・保存・構文確認は成功し、実行時に機器のネイティブ処理が異常終了したこと。通常のPython構文エラーや、Androidからの転送失敗として扱わない。なお、構文確認の成功だけで実行時の動作や全内容の同一性を証明するものではない。

このログには `[MPW DIAG ...]` と `[MPW MEM ...]` が含まれておらず、通常コードの実行ログだった。**「診断ログを保存」は現在のログの書き出しであり、診断版の作成・実行ではない。** そのため、この記録だけから異常終了した初期化段階や、BLE有効化・メモリ不足が原因であるとは確定できない。

Load access faultは無効なメモリアドレスへの読取りを示す。ゼロに近いアクセス先はNULLポインタ由来の可能性があるが、割当失敗・ファームウェアの不具合・状態破壊などの内訳までは特定できない。[ESP-IDF公式の例外説明](https://docs.espressif.com/projects/esp-idf/en/v5.5.4/esp32c6/api-guides/fatal-errors.html#instruction-access-fault-load-access-fault-store-access-fault)

次の確認は上記手順で診断版を準備して1回実行し、最後のBEFOREと対応するAFTER、Pythonの空き、ESP-IDF各ヒープの空きと最大連続領域を取得すること。初期化前にクラッシュした場合はFILE_ENTERが出ないこともある。ログの欠落や計測による条件変化も考慮し、特定の空き容量を共通の安全閾値としたり、GC・Wi-Fi停止・BLE初期化順変更で直ると保証したりしない。[ESP-IDF側のヒープ観測API](https://docs.micropython.org/en/v1.27.0/library/esp32.html#esp32.idf_heap_info)

ファームウェアの正確なネイティブ関数を調べる場合は、実機に入っているUIFlow2/MicroPythonビルドと一致するELF・デバッグシンボルで例外アドレスを解決する必要がある。似た版や別ビルドのELFから関数名を推測しない。Webアプリの診断・復旧機能はファームウェア内部のNULLアクセスを直接修復するものではない。

### 追加の診断版結果とBLE先行準備

その後の診断版では、`self.ble.active(True)` の直前の `[MPW DIAG 15]` まで出力され、直後の `[MPW DIAG 16]` が出る前にネイティブpanicが発生した。BLEオブジェクトの作成には到達したが、後続のサービス登録・広告には到達していない。有効化直前にはPython空き222,480バイトに対し、ESP-IDF側の空き合計12,448バイト、最大連続領域10,240バイトが記録された。作品開始時点からネイティブ側が圧迫されていたため、作品全文の読込み・コンパイル前にBLEを準備する経路を追加した。これらの診断値だけではクラッシュ内部の原因確定や、対策後の実機成功の証明にはならない。

利用者から、M5NanoC6 / UIFlow2 v2.5.3 / 37個のLEDを使う対象作品で、旧版の **Bluetoothを先に準備する（起動時のメモリ対策）** をONにすると動作したとの報告を受けた。これはその作品・組み合わせの確認で、ほかの作品や全機種の保証ではない。この報告を踏まえ、現行版はBluetoothを使うと判定できる作品に先行準備を自動適用する。手動ON/OFFは不要になった。

「プログラム」の実行欄で対象作品には **Bluetoothを自動で先に準備します** と表示する。コードの静的な `CONFIG` の `"wireless": True`、認識できるBLEのimport・`BLE()` 代入・対応する `active(True)`、または現在の画面に適用されている「AIの準備」のBluetooth有効設定（既存の機器・LED設定の対応判定を通したもの）を使って判定する。設定の対応判定はコード全文の一致や実行時の動作を保証しない。コードの `"wireless": False` を認識した場合は、それを優先して適用しない。起動中の作品を停止・古い準備参照を解放した後、新しい `.tmp` へ書き始める前にBLEを有効化する。既に有効ならそのまま使い、無効化やWi-Fi・GATT・NVS・作品コードの変更はしない。診断版のファイル自体へこの処理を追加する機能ではない。

比較するときは、元コードを保管して、書き込み処理の終了後に **完全な電源再投入 → USB再接続 → 自動準備の案内を確認 → 診断版を「実行」1回** の順に進める。本体ボタンやBLEを操作せず、`[MPW BLE PREP] BEFORE_ACTIVE` / `AFTER_ACTIVE` のメモリ値と成功マーカー、その後の `[MPW DIAG 15]` / `[MPW DIAG 16]` を確認し、診断ログを保存する。番号は今回の作品のものなので、他のコードではそのコードのBLE有効化前後を確認する。計測APIの `unavailable` は取得未対応であり、値が十分だった証拠にはしない。比較対象は旧版で取得済みの記録を使い、現行の先行準備を解除するために作品の無線設定を書き換えない。

BLE先行準備が失敗した場合は新しいプログラムを書き込まず、実行を止める。panic・再起動後は下記の明示的な復旧を行い、復旧できなければ電源再投入・再接続する。自動再試行はしない。先行準備後に後続処理が失敗してもBLEだけONのまま残る場合があるため、比較条件は電源再投入で揃える。このアプリからの実行経路は、保存だけや起動設定変更には適用せず、ファームウェアの電源投入時の自動起動経路も修正しない。詳細は[Bluetoothの先行準備](execution-memory.md#bluetoothの先行準備対象作品に自動適用)を参照。

## 異常終了した後の操作

起動ログが落ち着いてから **USB操作を復旧する** を押す。作品の停止を試してRaw REPLを再取得し、機器情報を読み直す。コードや自動起動設定は変更せず、作品を再実行しない。失敗する場合は **接続を切る → 電源を入れ直す → USBをつなぎ直す**。繰り返し再起動する場合は既存の電源投入時の復旧ガイドを参照する。

## 検証範囲

ホストテストで分割panic・ROM起動ログ、停止中の再起動、終了通知、古いセッションの破棄、同期前の書き込み禁止、診断版の構文木比較とAPI順序、保存・保管確認UI、9ロケールの案内を確認する。BLE先行準備は生成された有限Pythonコマンドのホスト実行で、有効化・既に有効な場合の維持・例外・参照解放を確認し、模擬USB/UIで対象作品の自動判定・書き込み前の順序・無線無効設定の優先を確認する。利用者提供の診断値と旧版の手動ONによる対象作品の動作報告は上記の観測として扱う。提供側による新版の自動適用経路・実機メモリ・Android USB/BLEの動作確認は **NOT RUN**。対象作品での比較と、原因に応じた修正後の実機確認が別途必要。

実機受入では、対象機種・UIFlow2版・給電条件を記録して、次を別々に確認する。

- 完全な電源再投入後、診断版のFILE_ENTER・初期化前後・Python/ESP-IDFのメモリログを取得できる。欠落・非対応APIも成功に読み替えない。
- ネイティブ異常終了後、保存成功と実行失敗が区別され、自動再実行されない。明示的なUSB復旧の後にだけ次の操作ができる。
- 原因に応じた修正を元作品へ適用した後、通常コードの起動、LEDの演出、本体ボタン、BLE接続・操作・切断・再接続、停止後の再実行を確認する。診断版や最小コードだけの成功で、作品の修正完了としない。
