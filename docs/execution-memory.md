# 書き込み・実行時のメモリ圧迫対策

## 目的と確認範囲

作品の演出・GPIO・LED数・輝度上限・BLE通信仕様を変更せず、WebアプリがRaw REPLへ送る保存・実行コマンドのメモリピークと不要な参照を減らす。作品のコードを短縮・書換えしたり、BLE・Wi-Fiを無断で無効にしたりする対策ではない。

調査のきっかけは、M5NanoC6 / UIFlow2 2.5.3で作品全体を実行すると `BLE.active(True)` の段階でネイティブの `Load access fault` が発生し、小さいLED＋BLEプログラムでは有効化できた事例。比較ログでは、失敗側のESP-IDFの空き合計が11,824バイト・最大連続領域が10,240バイト、成功側の有効化直前は空き合計192,068バイト・最大連続領域180,224バイトだった。成功側の有効化前後の空き合計差33,408バイトは、その試行の観測差分にすぎず、BLEの固定必要量や安全閾値ではない。

この比較はネイティブ側のメモリ圧迫を疑う根拠だが、クラッシュ箇所を対応ELFで特定した証拠ではない。その後、利用者からM5NanoC6 / UIFlow2 v2.5.3 / 37個のLEDを使う対象作品で、旧「Bluetoothを先に準備する」をONにすると動作したとの報告を受けた。これはその組み合わせの利用者確認であり、全機種・全ファームウェア・全作品の保証ではない。今回の自動適用経路そのものの提供側実機確認は **NOT RUN**。ホストテスト・ビルドの成功と、実機で作品が正常に動くことを区別する。

Python側の空き表示だけでネイティブ通信の余裕を判断しない。必要時は対象ファームウェアのAPI対応を確認し、[ESP-IDFヒープ情報](https://docs.micropython.org/en/v1.27.0/library/esp32.html#esp32.idf_heap_info)の各領域の空き・最大連続領域も比較する。`gc.collect()`は参照されなくなったPythonオブジェクトの回収を補助するが、ESP-IDFの空き領域回復やネイティブpanicの解消を保証しない。

2026-10-08の追加診断では、作品内の `self.ble.active(True)` 直前の `[MPW DIAG 15]` まで到達し、対応する `[MPW DIAG 16]` が出る前に `Load access fault` が発生した。有効化直前のPython空きは222,480バイト、ESP-IDF側の全領域の空き合計は12,448バイト、最大連続領域は10,240バイトだった。Pythonとネイティブ側の空きは別の指標であり、合算しない。この結果はBLE有効化時のネイティブメモリ圧迫を疑う根拠だが、割当失敗から異常終了に至る内部処理の確定には一致するELFが必要。利用者の先行準備成功の報告を踏まえ、Bluetoothを使うと判定できた「実行」には以下の先行準備を自動適用する。

## 変更前と変更後

作品全文に対する処理を比較する。Raw REPLへ送る小さな管理コマンド自体のコンパイル回数とは別。

| 項目 | 変更前 | 変更後 |
| --- | --- | --- |
| 「実行」1回の作品全文コンパイル | 一時ファイル確認、保存後確認、起動時の計3回 | 一時ファイルで1回。確認した同じコードオブジェクトを起動 |
| ソース全文の参照 | REPLの `s` / `source`、実行用 `namespace` が残り得る | 全文は準備関数のローカルだけ。準備完了後は参照を残さない |
| 保存後・起動直前の照合 | 保存後の全文読込・再コンパイル | 384バイトずつ読み、サイズとSHA-256を照合 |
| 保存だけの「プログラム更新」 | 全文読込で構文確認 | 構文確認は維持し、実行用コードを保持しない |
| 保存済みプログラムの読込 | 全文と全文Base64を機器で生成 | 384バイトずつBase64出力。ブラウザで結合・復号 |

作品全文のコンパイル時にはソースとコンパイル結果を同時に必要とするため、メモリ不足を完全になくす変更ではない。常駐する作品の関数・状態・LEDバッファも必要な間は保持される。

## 「実行」の順序と安全確認

1. 実行中の作品があれば停止し、完了を確認する。停止を確認できなければ新しい書き込みを始めない。
2. Bluetoothを使うと判定できたコードの「実行」では、古い実行準備とWriter所有のソース参照を解放してGCを行い、下記の小さい有限BLE準備コマンドを自動で実行する。手動ON/OFFは不要で、成功を確認できなければファイル転送へ進まない。Bluetoothを使わないと判定したコードにはこの追加処理を行わない。
3. ホスト側の古い準備情報を無効化し、ブラウザで編集内容のUTF-8バイト列のサイズとSHA-256を計算して、新しい準備トークンを作る。旧Writerが残していた `s` / `source` / `namespace` と古い実行用コードへのREPL側参照を外し、GCを行う。辞書の内容を破壊したり、作品のソースを書き換えたりはしない。その後、従来どおりBase64チャンク（既定384バイト）で `main.py.tmp` へ書く。
4. 準備関数の中で `.tmp` 全文を読み、期待サイズ・SHA-256を確認してから1回だけ `compile(..., mainPath, 'exec')` を行う。失敗したら既存の `main.py` を昇格・実行しない。成功時はコードオブジェクトとトークン・保存先・ハッシュ・サイズを準備情報として保持し、ソース全文の参照と準備関数を片付ける。
5. 従来の退避・昇格手順を維持する。古い `.bak` を削除し、既存 `main.py` を `.bak` へ退避、`.tmp` を `main.py` へrenameし、対応時はsyncする。昇格失敗時はバックアップ復旧を試みる。これは電源断を含む完全なトランザクション保証ではない。保存後のファイルサイズも確認する。
6. 昇格と保存確認の成功後だけ、ブラウザ側を実行準備済みにする。保存後の確認と実行コマンド内の起動直前確認では、準備情報のトークン・保存先・SHA-256・サイズが一致することを確認し、保存ファイルを384バイトずつ読んで再照合する。
7. 確認関数とチャンクへの参照がなくなった後、準備情報からコードオブジェクトを取り出して単発の `exec` に渡す。`__name__='__main__'` と保存先に対応する `__file__` を設定する。ここでは作品全文の再読込・再コンパイルをしない。
8. 正常終了・Python例外・Ctrl-C終了時は `finally` で準備情報を除去しGCを試みる。ネイティブpanicや電源断でPythonの後始末が必ず動くとは扱わない。

ホストの準備情報は起動時に消費するため、同じ準備を繰り返し起動しない。ソフトリセットなどで機器側の準備が失われた場合や古いトークンは `PROGRAM_NOT_PREPARED`、保存内容が同サイズでも変わった場合は `PROGRAM_CHANGED` として実行を拒否する。利用者は通常どおり再度「実行」し、編集内容から書き込み・準備をやり直す。機器ファイルを黙って再コンパイルして失敗を回避しない。

SHA-256は保存内容と準備したコードを対応させるための整合性検査であり、悪意ある機器に対する認証・署名検証ではない。対象MicroPythonには `hashlib.sha256` が必要。未対応・import失敗・計算エラー時は安全側で停止し、検査を黙って省略したりサイズ確認だけへ切り替えたりしない。対象UIFlow2版で実機確認する。

## Bluetoothの先行準備（対象作品に自動適用）

「プログラム」の実行欄に、対象作品では **Bluetoothを自動で先に準備します** と表示する。旧版の手動チェックボックスはなく、対象作品の「実行」には必ず適用する。「プログラム更新」などの保存だけ、接続だけ、自動起動の設定変更では実行しない。

判定は実行時のコードと、現在の画面に適用されている準備設定を使う。コードの認識できる静的な `CONFIG` 辞書に `"wireless": True` がある場合、認識できるBLE初期化がある場合、または「AIの準備」のBluetooth有効設定（`profile.features.ble === true`）がAppの既存の機器・LED設定の対応判定を通した場合が対象。対応判定はコード全文のハッシュ一致や実行時の動作を証明するものではない。BLE基準コードの実機確認登録の有無をBluetooth有効設定と混同しない。コードの静的な `CONFIG` に `"wireless": False` がある場合は、それを優先して先行準備を行わない。

標準入門コードの `CONFIG = json.loads('...')` も対象にする。モジュール直下の `json` / `loads` のimportと別名を照合し、対応する単一の通常のPython文字列を復号してブラウザ側でJSONを解析する。動的な引数や別名の上書きを確定値として採用しない。無線OFFの入門コードにも共通BLE実装が含まれるが、その設定値を優先するため先行準備しない。

BLE初期化の検出は、ブラウザ内の構文解析で `bluetooth` のimport、引数なしの `BLE()` の代入、それに対応する `active(True)` を確認する。対応するaliasと `from bluetooth import BLE` も扱うが、コメント・文字列内の例は対象外。任意の動的初期化・全alias・実行時に書き換わる設定をすべて判定するものではなく、条件分岐の実行や実機のBLE対応を保証しない。作品のソースは実行せずに解析し、対象にならないコードを勝手に書き換えない。

利用者が押した「実行」の停止確認後、古い準備情報とWriter所有のソース参照を解放してから、小さい有限Raw REPLコマンドでBLEのシングルトンを取得する。**`main.py.tmp` の作成・ファイル転送・作品全文の読込みやコンパイルより前**に、未有効の場合だけ `active(True)` を呼ぶ。既に有効なら有効状態を維持し、OFF→ONにはしない。最後に `active()` がtrueであること、stderrなし・正常完了・`__M5_BLE_PREPARED__` が揃った場合だけ書き込みへ進む。

準備コマンドは `[MPW BLE PREP] BEGIN` と `BEFORE_ACTIVE` / `AFTER_ACTIVE` のPython・ESP-IDFヒープ情報を記録する。計測APIがない・取得できない場合は `unavailable` とし、BLE本体の失敗を成功に読み替えない。計測関数とBLEのPython参照は有限コマンドの終了時に手放し、作品のソース全文は保持しない。ネイティブのBLEスタックは有効のままで、作品が自身のGATT・広告・IRQを設定する。

先行準備はWi-Fi、GATT、広告、IRQ、NVS、自動起動設定、作品コードを変更せず、BLEの解除も行わない。準備失敗時は新しいファイルを書き始めずに停止する。ネイティブpanic・再起動を検出したらRaw REPLの明示的な復旧または電源再投入・再接続が必要で、自動リセット・自動再試行はしない。先行準備が成功しても、その後の転送・構文確認・起動が失敗する場合があり、**BLEだけがONのまま残ることがある**。停止・失敗時に元の有効状態へ自動で戻すものではない。

これは大きな作品のコンパイルより先にBLEのネイティブ領域を確保する実行経路であり、空きを増やす保証やファームウェア内部の修正ではない。BLEの保持によって後続コンパイルに使える領域が減る可能性もある。コード先頭へ同じ処理を挿入する変更とは異なり、ファームウェアからの電源投入時の自動起動には適用されない。USBから起動できても、自動起動のクラッシュ解消とは扱わない。

### 同じ作品での安全な比較

1. 元コードと必要な機器設定を退避する。起動設定・Wi-Fi・演出・LED配線は比較のために同時変更しない。
2. 書き込みなどが終わっていることを確認し、機器の電源を完全に切って入れ直す。USBを接続し直し、必要ならRaw REPLを明示的に復旧する。前回のBLE有効状態を引き継ぐ再実行だけでコールド起動の比較をしない。
3. 同じ診断版でBluetooth先行準備が自動適用される案内を確認し、「実行」を1回だけ押す。ON/OFFの選択は不要。起動中に本体ボタン・BLEを操作しない。「実行」は機器の `main.py` を上書きする。
4. `[MPW BLE PREP] BEFORE_ACTIVE` / `AFTER_ACTIVE` と各メモリ値、成功マーカー、その後の作品診断ログを取得する。今回の対象作品では `[MPW DIAG 15]` / `[MPW DIAG 16]` が揃うか確認する。番号は診断元のコードに依存し、別作品で同じ番号とは限らない。
5. 旧版で先行準備をOFFにしていた既存記録と比較する。比較のためだけに現行の安全処理を解除したり、作品の無線設定を変えたりしない。元作品でも別途、起動・LED・本体ボタン・BLE接続と操作・停止後の再実行を確認する。クラッシュが解消しなければ再試行を繰り返さず、ログを保存して調査する。

記録はPASS / FAIL / NOT RUNと、アプリ版・先行準備の適用有無、コールド起動か再実行かを分ける。旧版の手動ONでの利用者確認と、新版の自動判定・適用の実機確認は別に記録する。ホストテストで順序・例外・参照寿命がPASSでも、ESP32のメモリ・クラッシュ・LED・無線の実機確認は代替できない。

## CONFIGのメモリ使用量

`CONFIG` の辞書、`modes` / `actions` のリストと辞書、名前・表示ラベルなどの文字列も、Pythonヒープを使う。ゼロコストではないが、少数のモード・アクションを持つ設定だけを今回のネイティブメモリ不足の主因とする証拠はない。診断ではPython側に222,480バイトの空きがある一方、ESP-IDF側は圧迫されていた。両者の空き量を同じものとして扱わない。

今回の対策は作品全文を読み込んでコンパイルする前にBLEを有効にする順序変更であり、`CONFIG` を削除・書き換えない。機器からWebコントローラへ送る作品名・モード・アクションの表示ラベルも保全する。大量のモードや巨大な配列、画像・演出の事前計算表を追加した場合は、設定データの大きさや重複コピーも改めて確認する。

`self.config = config` や `self.modes = config["modes"]` のような代入は、既存のオブジェクトへの参照を保持するもので、辞書・リスト・文字列の全文コピーではない。対して、追加の辞書・リストを組み立てたり、毎フレーム設定をJSONへ変換したりすれば、その分の割り当てが増える。[MicroPythonのオブジェクトと文字列のメモリ管理](https://docs.micropython.org/en/v1.27.0/reference/constrained.html#string-operations)

実使用量を調べる場合は、同じファームウェアで `gc.collect()` 後の `gc.mem_alloc()` を設定生成の前後で比較する。この差分は実行時に増えた分であり、すでにコンパイル時に確保された文字列・コードのコストまで含むものではない。結果は対象ビルド・文字列の共有・他の初期化や測定自体の割り当てに依存するため、未測定の固定バイト数は断定しない。設定だけを測る独立した診断で比較し、BLE用のネイティブ空きは別に `esp32.idf_heap_info()` で観測する。普段の利用者へこの計測を必須にしない。

## 保存だけ・読み込み・後始末

「プログラム更新」は同じ `.tmp` のサイズ・SHA-256・構文確認を行うが、コードオブジェクトを実行準備として保持せず、その場で参照を手放す。保存に成功しても今すぐ作品を動かしたとは表示しない。元の自動起動設定を勝手に変更しない。

準備・照合・昇格などの失敗時には、使えなくなった準備情報を破棄する。USB切断などで機器側の後始末ができなくても、その準備をホスト側で再利用しない。再実行は新しいトークンで最初から準備する。バックアップ復旧・ファイル削除も準備情報を破棄してから実施する。

「保存済みのプログラムを読む」は、機器でサイズ上限（既定256KiB）を確認し、384バイトずつ読んでBase64を出力する。ファイルと読込関数は終了時に片付ける。384は3の倍数なので、中間チャンクにBase64のパディングが入らず、従来の `__FILE__` の1行としてブラウザ側で結合・復号できる。ブラウザ側でも復号後サイズを確認し、機器のstderrは読込失敗として扱う。これは機器側のメモリ対策であり、ブラウザが編集用コード全文を保持しなくなるわけではない。

## AIに渡す準備文

日本語・英語・簡体字中国語の準備文と修正依頼に、バッファ再利用、有界キュー、過大な事前計算表や毎フレームの大きな割り当ての回避、全文の多重保持・再コンパイルの回避を含める。作品の演出と安全設定を維持し、GCだけで解消すると保証させない。コピーとUTF-8保存は同じ全文を使う。詳細は[AIの準備](ai-preparation.md#メモリ圧迫対策の共有)と[教材原典](../prompt.md)を参照。

この準備文の更新だけで既存の作品コードは変わらない。また、既存作品へ不要な計測コードやヒープ解析の作業を一律に要求しない。通常の利用者には「準備 → 実行 → 実物確認」を案内する。

## 実機受入手順（未実施は NOT RUN）

実施者は、元作品・機器設定・自動起動設定を記録し、必要な元コードをPCへ退避する。「実行」は機器の `main.py` を保存し直す。Wi-Fi設定やファームウェアを同時に変更せず、比較条件を揃える。ログ共有時にはSSID、アクセスコード、資格情報などの機密情報を除く。

1. **コールド起動**：対象機器の電源を完全に切って入れ直す。対象機種・UIFlow2版を確認してUSB接続し、元の作品全体を新しいWriterで「実行」。起動直後には本体ボタン・BLEを操作せず、書き込み確認、作品の起動、BLE有効化、メインループ到達と再起動の有無を確認する。必要な診断ログだけを別の診断版で取得し、元作品と区別する。
2. **BLE操作**：Webコントローラから接続し、機器の状態通知を受信する。明るさ、再生・停止、モード、アクション、本体ボタンを作品仕様に従って操作し、画面の状態と実物のLEDを比較する。ACTION再押下・200ms消灯などの既存挙動を変えていないことも確認する。
3. **切断・再接続**：BLEを明示的に切断して再接続し、状態通知・操作を再確認する。途中の送受信データが混ざらず、再接続を繰り返しても停止・再起動しないことを確認する。回数と結果を記録する。
4. **停止・再実行**：USBの「停止」で終了と可能な範囲のLED/BLE後始末を確認してから「実行」。続いて、実行中に編集して停止を手動で押さず「実行」し、旧作品の停止完了後に新しい内容だけが動くことを確認する。BLEが切断された場合は再接続し、各回の状態と実物を確認する。
5. **保存だけ・読込**：「プログラム更新」で保存しても作品が起動しないことを確認する。「保存済みのプログラムを読む」で日本語を含む全文と末尾が一致することを確認する。その後「実行」で新しい準備が作られることを確認する。
6. **電源投入時の動作**：既に自動起動を使う作品なら、明示的に保存した同じ作品を電源再投入で確認する。自動起動ではファームウェアの起動経路を使い、Writerの準備コードを通らないため、USBからの実行成功だけで自動起動も成功としない。試験のために自動起動を勝手に変更しない。
7. **実装者の異常系確認**：テスト用機器と退避済みファイルだけで、構文エラー、同サイズの保存内容変更、古い準備、準備後のリセット、転送中断を試す。新しい作品の起動を拒否し、失敗を成功表示にしないことを確認する。通常利用者へこの作業を要求しない。

受入記録には対象の機種・UIFlow2版・作品コードの識別情報、実施操作、結果（PASS / FAIL / NOT RUN）を残す。ホストの模擬テストで実行回数・参照寿命・整合性検査を確認できても、MicroPythonの実メモリ、無線接続、電源や実際の発光は別の確認である。

## 実装の入口

- [`ProgramCommands.ts`](../src/services/micropython/ProgramCommands.ts)：機器側の準備・ストリーム照合・単発実行・後始末コマンド。
- [`BlePreflight.ts`](../src/services/micropython/BlePreflight.ts)：対象作品の「実行」に自動適用する有限BLE先行準備コマンド。
- [`bleProgram.ts`](../src/services/editor/bleProgram.ts)：無線設定とBLE初期化の構文検出による先行準備対象の判定。
- [`FileTransferService.ts`](../src/services/micropython/FileTransferService.ts)：SHA-256生成、チャンク転送、検証、既存退避・昇格、読込。
- [`MicroPythonDevice.ts`](../src/services/micropython/MicroPythonDevice.ts)：準備情報を使った確認・起動、停止確認。
- [`programCommands.test.ts`](../src/test/programCommands.test.ts)：CPythonホスト上の生成コマンド検証。MicroPython実機の代用ではない。
