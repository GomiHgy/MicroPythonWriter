# 入門プログラム：提供側の実機受入

## 現在の配布状態

`firmware/starter/runtime.py` と `StarterProgram.ts` は、提供側が検証するための候補実装。**M5NanoC6 / AtomS3Lite と対象UIFlow2の組合せで、実機受入を完了したプログラムはまだない。** `providerVerifiedStarters` は空のため、現時点の `starterAvailability()` は常に `verified: false` を返す。利用者の「動作OK版」保存・AI基準コード登録を、提供側の受入証明として使わない。

将来の提供側記録は、リポジトリ内の `ProviderStarterVerification`（受入した生成コード全文 `source`、ISO日時 `confirmedAt`、担当者 `confirmedBy`、証拠の所在 `evidencePath`）としてレビューする。生成コードとの全文一致・記録項目の存在を照合するため、設定・演出・ランタイムの変更も未確認へ戻る。作品JSONやブラウザ保存からこの表を追加・変更しない。照合ロジックがあることと、実在する受入済み記録があることは別である。

設定が有効なら、実機未確認の候補も「試すコードを準備」で編集画面へ用意し、表示・保存・ダウンロードできる。これらはソフトウェア上の操作であり、USB接続や機器への実行・書込みを自動で行わない。未確認候補を一般利用者に「まず動く」「確認済み」と表示しない。

「AIの準備」でWebコントローラを使う場合の「対応プログラムを準備」も、`ControllerStarter.ts` から同じ生成器を呼び出す。ブラウザ内の作品を確認・一時退避して候補へ置き換えるだけで、機器には送らない。通常利用者には基準コード登録を求めず、候補全文と未確認の注意をAI準備文にも収録する。有効な登録済みv1/v2コードは候補より優先し、登録情報を試用から作成・昇格しない。

機器で試すには、利用者がUSB接続と実行を別々に操作する。未確認候補の実行は毎回警告と確認を表示し、機種・UIFlow2の正確な版・外付けLEDのGPIO／個数／最大輝度・配線・電源を確認する。実行時には動作中のプログラムを停止し、`main.py`を保存し直して起動することも明示する。キャンセルした場合、その実行操作によるUSB書込み・停止・起動を行わない。不正な設定、検出機種の不一致、処理中などの実行不可条件は解除しない。これらの確認は電気的安全や対象ファームウェアでの動作を保証するものではない。

試行の確認と提供側の実機受入は別である。「確認済み」と表示するには、この受入を提供側が完了し、証拠と一致する対応表を別途コードレビューして追加する。利用者が警告に同意したり「動作OK版」を保存したりしても、`verified` やAI用BLE基準コードの確認情報には反映しない。

## 候補の範囲

- 外付けRGB LED 1〜300個、GRB、BPP 3、`machine.bitstream()` のencoding=0と固定 `(400, 850, 800, 450)` ns。`LED_RESET_US = 350`を設定し、実送信の前後それぞれGPIO LOWと350µs待機を行う。同じ最終GRB出力の通常再送とその待機は省略する。NeoPixel追加ライブラリは使用しない。
- GPIOは利用者設定。NanoC6ボタン9 / AtomS3Liteボタン41を使い分け、既知の内蔵LED・ボタンとの衝突を拒否。数値範囲内でも出力可能・外部端子に出ている・他用途と衝突しないことは保証しない。
- 起動時は消灯。短く1回・短く2回・長押しのそれぞれに、次の光り方／点灯・消灯切替／何もしないを設定する。旧作品の長押し消灯も互換性のため保持する。チャタリング40ms、長押し800ms。長押しは1回だけ実行し、解放時に短押しを重ねない。
- 2回押しは1回目の安定した解放から2回目の安定した押下まで350ms未満で判定し、2回目も短く解放した場合に実行する。350ms以上なら1回目を確定し、次の押下を別の操作として扱う。1回押しは350ms待つ。2回押しが「何もしない」でも1回押しを重ねず、時間内の2回目が長押しなら長押しだけを実行する。待ち時間はLED・BLE更新をブロックしない。
- 「押している間だけ光る」は3種類の押し方の割り当てより優先する。800msを超えて保持しても長押し処理をせず、解放で消灯し、1回押し・2回押しの遅延処理も残さない。
- 本体ボタンを使用せず、押下中動作も無効で3種類の割り当てがすべて「何もしない」の場合、ボタンGPIOを初期化・読取りしない。AIの準備で本体ボタンをOFFにした無線候補もこの設定を使う。
- 単色・虹色・流れる光・きらめき。速度、0=無限の繰返し、有限回の終了時に保持/消灯。全出力に設定輝度上限を適用し、消灯→点灯には200ms以上の非ブロッキングフェード。
- 無線有効時だけ標準 `bluetooth.BLE` を開始。NanoLED v2、選択したモード、組込み1回アクション `SPARKLE`（約1秒）を提供。この候補は作品で指定がない場合の既定動作として、演出中の追加ACTIONも受け付け、最後の実出力から200ms補間で再スタートする。最後の受付から約1秒後に、最初の演出前のモード位相・再生状態へ戻る。再押下で復帰元を上書きせず、後で実行する演出キューは作らない。独自作品に「実行中の追加ACTIONは無視する」などの明示指定がある場合は、AIによる生成・修正でその指定を優先して実装する。候補の再スタート動作をすべての作品へ強制せず、変更したコードは別途実機確認する。
- BLE RX有界8チャンク、行128バイト、実コマンドLF込み20バイトまで。過大/不正行・キュー超過は破棄。TXは20バイトずつ、送信中行は固定、待機は最新1件、最大5件/秒、周期約1秒。Notify失敗は3回までで接続を終了。初回STATUSを受けるまで通知しない。
- `STATUS` / `PLAY` / `PAUSE` / `OFF` / `MODE <id>` / `ACTION SPARKLE` / `BRIGHTNESS n` / `SPEED n`。停止は保持、消灯は黒。送信済みRGBを報告し、物理発光を計測した値とは扱わない。

UIFlow2の各リリース・各ボードでAPI搭載や挙動が同じとは推定しない。特に、LEDタイミング、リセット時間、Bluetoothとbitstreamの同時負荷、Pythonメモリ・JSON Unicode符号化は実機で確認する。対応範囲の最大カタログでJSONが4096バイトを超えた場合もフェイルクローズで終了し、短縮して誤った状態を送らない。

### LED送信と固定バッファ

ちらつきを抑えるため、同じ表示の不要な再送を減らす。候補フレームと最終正常送信済みフレームを別々の再利用bytearrayに保持し、最大輝度・利用者の明るさ・フェード・補間・消灯を適用したGRBを比較する。内容が同じでも、初回の全消灯と例外・KeyboardInterrupt・安全停止は強制送信する。実送信は全LED分を1回で送り、bitstreamと末尾のLOW保持が成功してから送信済みキャッシュをコピー更新する。送信例外では無効化し、可能な限りLOWへ戻して既存のエラー経路へ渡す。再試行ループや失敗の成功扱いはしない。

再送の省略は主ループの省略ではない。演出時計・位相・有限回・ACTION/フェード完了・基準色・`output_reference`・復帰位相・入力・BLE通知を独立して進める。明るさ0や量子化による同一出力でもplayingの論理状態は進み、pausedなら止まる。LED dirtyとBLE dirtyは別管理とし、STATUSと周期通知を維持する。OFF・PAUSE・ACTION再押下は最後のソフトウェア送信済み出力の固定スナップショットを使い、作業バッファとの共有や輝度の二重適用を避ける。静的表示の不要な再描画のみ省き、動的モードの描画が必要なら維持する。一律FPS制限は加えない。

既存の候補GRBバッファに、最終送信済みGRBバッファ **`LED_COUNT × 3` バイト** を追加する。両バッファのペイロード合計は `LED_COUNT × 6` バイト。追加分は1/37/88/90/110/300個で3/111/264/270/330/900バイトであり、bytearrayオブジェクト・管理フラグ・アロケータの整列など実装依存の管理領域はこの計算に含まない。既存のRGB出力・復帰・補間用構造は別に残るので、プログラム全体のRAM増減や実機ヒープの余裕をこの値だけで保証しない。LED数の加算や固定化、設定・保存スキーマの追加はしない。

`StarterProgram.ts` は `runtime.py?raw` を生成コードへ全文埋め込み、`ControllerStarter.ts` も同じ生成器を使う。新たにコードを準備する両経路へ反映するが、既存作品・登録基準コード・確認記録は書き換えない。Web更新だけでは機器の `main.py` は変わらず、対応コードの再準備と利用者の明示的な書込み・実行・実物確認が必要。自動起動設定も変更しない。登録基準コードと新ルールが衝突する場合は差分と再確認の必要性を示し、改造後は元の実機確認を流用しない。

M5NanoC6 + UIFlow2 v2.5.3 + WS2812B-MINIの一作品で利用者から改善報告があったが、複数対策をまとめて適用した観察であり、個別対策の効果・原因・他構成での改善を証明するものではない。350µsは採用候補値で、全WS2812系列・配線での保証値ではない。「最終送信済み」はソフトウェア上の正常終了であり、物理発光の測定やLEDの独立電源リセットの検出はしていない。更新した候補も **実機未確認** のままとする。

## 受入手順

1. 提供側が配線・電源・LEDのRGB仕様を確認し、記録表を埋める。低い輝度・少数LEDから始める。GPIO設定だけで電源容量の安全を保証しない。
2. 正確なUIFlow2版に対し、まず無線なし候補をUSB実行。起動消灯、全LEDの赤/緑/青と順序、安全上限、40ms未満の接点揺れを確認。下の「ボタン操作の必須受入」を全項目実施する。
3. 押している間のレシピで押下開始・200ms以上の点灯フェード・解放消灯を確認。800ms以上保持しても長押し・1回押し・2回押しが割り込まず、解放後も遅延操作が起きないことを確認。フェード中に停止/消灯しても応答し、点灯中の色切替でフェードをやり直さないことを確認。
4. 4種類の演出で速度0/50/100、有限回の保持/消灯、無限繰返し、再生停止後の位相維持、明るさ0/50/100を確認。連続使用時の電流・発熱も確認。
5. 無線あり候補へ変更し、[v2実機受入](ble-protocol.md#v2実機受入未実施はnot-run)を全項目確認。SPARKLE後のplaying/paused/off復帰、連打不蓄積、PLAY/PAUSE/MODE/OFFによる中断を含む。
   - SPARKLE中の再押下で、黒や元モードへ瞬間的に戻らず、現在の実出力から200msで新しい演出へつながることを確認する。連続して再押下しても復帰先は最初の演出前の状態で、最後の受付から約1秒で完了し、予約された古い演出が始まらないこと。補間中のPAUSEは見えていた光を保持し、明るさ調整・PLAYの基底位相再開・OFF・安全停止も確認する。未定義ACTIONでは進行をリセットしない。時刻カウンタ周回・複数LED・明るさ0も対象とし、実機確認は **NOT RUN**。候補のカタログはSPARKLEのみなので、独自コードで複数ACTIONを定義する場合は異なるIDへの切替も別途受入する。
   - リモコンの `OFF` が最後の出力色から200msで消灯することを、点灯中・停止中・点灯フェード中・アクション中に確認する。輝度設定と選択モードが保持され、繰り返し `OFF` や `PAUSE` で消灯が遅れず、消灯途中の輝度変更で明るさが跳ね上がらないことも確認する。通知は実際に送信した出力を反映し、黒になる前に `playback=off` と報告しない。起動・例外時の即時消灯は従来どおり。実機確認は **NOT RUN**。
6. 日本語・中国語・絵文字ラベル、最大8モード・最大300LEDの20バイト分割通知、連続書込み、行/キュー超過、通知停止、抜線・電源断、再接続、USB再実行後の復帰を確認。途中行が別接続へ混ざらないことを確認。
7. USBの永続更新は別操作として実施し、電源単独で電源再投入。PC・スマホを接続しない本体ボタン動作も確認。「プログラム起動」と「作品が正しく動く」を別々に記録。
8. FAILを修正して再試験。全必須項目と証拠が揃ってから、レビュー付きで検証済み対応表/配布物/ハッシュ照合を実装する。現段階の空レジストリや `verified: false` を利用者が切り替える手段は用意しない。

### ボタン操作の必須受入

すべて **NOT RUN**。時間はチャタリング対策後の安定状態を基準に記録する。境界はホストテストだけでなく、対象UIFlow2・LED負荷・無線負荷での実際の読み取り周期も確認する。

- 1回・2回・長押しそれぞれに3つの選択肢を割り当て、選んだ処理だけが1回動く。「何もしない」で他の押し方へ読み替えない。
- 1回目の解放後、350msが経過する前は1回押しを実行しない。2回目がなければ経過後に1回だけ実行する。
- 解放から2回目の押下まで349msなら2回押しの候補、350ms・351msなら別の押下になる。2回押しと判定した場合、2回目の解放時に1回押しを追加しない。2回押し＝何もしないの場合も1回押しを抑止する。
- 799msの押下は短押し、800ms以上は長押しとして扱う。押し続けても長押しを繰り返さず、離しても短押しを起こさない。旧長押し＝消灯の互換動作も確認する。
- 350ms未満に始めた2回目を800ms以上保持すると長押しだけを実行し、1回目の短押しや2回押しを実行しない。
- 連打・接点揺れ・時刻カウンタの周回付近でも意図しない重複操作がない。待機中・長押し中もLED更新とBLE通信が続く。
- 旧作品を読み込んでもコード・動作OK版を自動更新しない。2回押しの既定値補完・旧長押し設定の保持を確認し、コード再準備・実行後に新しい割り当てで再試験する。

### LED送信のちらつき抑制の受入

現時点はすべて **NOT RUN**。同じ条件の旧コードと新コードを必要に応じて比較し、見た目だけで原因や個別対策の効果を断定しない。対象機種・UIFlow2版・実接続LED数・電源・配線・信号波形を記録し、実LED数に2を加える等の対策を混在させない。

- BLE未接続と接続中の両方で、静的点灯・連続アニメーション・短い点滅・有限回の演出を低輝度と設定上限輝度で確認する。明るさ0で進行後、明るさを戻したときの位相も確認する。
- OFF→PLAY/MODE/ACTIONの最低200ms点灯フェード、Web OFFの200ms消灯、フェード中MODE、OFF連打、PAUSE/PLAY、ACTION再押下・補間途中PAUSE/OFF・元状態への復帰を確認する。
- 起動時・停止・例外時に黒が送られることを確認する。LEDの電源だけを入れ直したときの復帰は自動検出されると仮定しない。
- LEDが変化しない期間もSTATUS応答・約1秒通知・本体ボタン・接続・切断・再接続を確認する。通知のpixelsと実物の色を別々に記録する。
- USBで停止した後の再実行、BLE再接続、PCなしの電源起動を確認する。自動起動変更は必要なら別の明示操作として実施する。
- 電源容量・GND・DATA配線・信号品質・LED型番・ファームウェア依存は未確認要因として残す。ちらつきが残る場合に送信省略だけを原因や解決策と断定しない。
